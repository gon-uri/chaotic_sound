# Compute cost of a dynamical box

Scripts: `lab/scripts/studies/cost.py` (from `lab/`: `caffeinate -is uv run python scripts/studies/cost.py`,
about 4.5 min wall; `--js-only N` reruns only the JavaScript part N times and merges it) and
`lab/scripts/studies/rk4_bench.js` (the JavaScript benchmark; `rk4_bench.html` runs it in a browser).
Numbers: `lab/outputs/studies/cost/results.json`, `summary.md`, `js_jsc.json`. Figures (gitignored,
regenerated by the script): `cost_vs_substeps.png` and `breakdown.png` in the same folder.

## Question

How expensive is one dynamical box? What does that imply for the planned real-time engine
(TypeScript in an AudioWorklet, 128-sample render quanta at 48 kHz, so a budget of 2667 µs per
quantum)? How many boxes fit in ≤ 50 % of one core, and is WebAssembly needed?

## Method

- **Machine.** Apple M1 Pro (8 performance + 2 efficiency cores, up to 3.2 GHz), macOS 14.3.1,
  Python 3.14.6, numba 0.68.0, numpy 2.5.4.
- **Python engine.** For each system × note {A1, A3, A5, A7} × {static knob at the default u, a
  full-range 4 s sine LFO on `param`}, I rendered 4 s of audio and measured:
  - `Dynamical.process` in 128-sample chunks (one render quantum) and in 512-sample chunks (the
    `Patch.render` default);
  - `render_tuned` alone, on the same per-sample p and Δτ arrays, in one call;
  - the cost of one RK4 step: `integrate_sampled` with 1000 steps per stored sample;
  - a per-stage breakdown of `process`, from an instrumented copy whose output is bit-identical to
    the real block;
  - the fixed cost per `process` call, from a linear fit of time per call against chunk length
    (16 … 16384 samples).

  Warm-up calls keep compile time out of every timing. Timings are thread CPU time, the minimum of 3
  repeats (5 for step costs).
- **JavaScript.** `node` is not installed. Instead I ran the benchmark with Apple's JavaScriptCore
  shell (`jsc`), which ships with macOS. JavaScriptCore is Safari's engine (here the Safari 17.3
  version) and has full optimizing JIT tiers. **V8 (Chrome) was not measured.** The benchmark has
  three implementations:
  - **A, specialized**: code generated per system, with the RHS inlined and the state in scalar
    local variables;
  - **B, literal port**: a line-by-line port of the Python kernels (`rhs(x, p, out)` on
    `Float64Array`s, a shared `rk4Step`). It runs *monomorphic* (one code copy per system) and
    *megamorphic* (one copy shared by all five systems);
  - **C, full box**: A plus everything else `process` does per sample. That is both smoothers,
    u → p, the P/μ/σ table lookup (reproducing `np.interp` exactly), normalization, the DC
    blocker and the safety check. C is called once per 128-sample quantum, writes `Float32Array`
    outputs and allocates nothing.

  Two more tests: two independent states stepped in one loop (a latency test), and five multi-box
  patches whose outputs are summed into one bus. Timings are wall clock, the minimum over
  3 runs × 3 repetitions, each after a JIT warm-up run.
- **Native ceiling.** The Lorenz and Rössler RK4 loops, hand-written in numba with scalar locals.
  This is LLVM-optimized machine code, so it bounds what WebAssembly could reach.
- **Checks.**
  - JS kernels A and B reproduce numba bit for bit in all five systems: the difference is 0 after
    about 10 periods.
  - The JS box output matches the Python block to ≤ 3·10⁻⁸ over 0.1 s, which is float32 output
    rounding. Cases: Lorenz A3 static and with LFO, Rössler A5 with LFO, Duffing A3 with LFO.
  - The scalar numba kernels are bit-identical to the engine kernel.
- **Load.** Other studies ran on the machine at the same time (load average 8–55 on 10 cores). CPU
  time and min-of-N reduce this effect but do not remove it (see Uncertainties).

## Results

### 1. Sub-steps per sample

n = ⌈Δτ/h_max⌉ = ⌈N·(P(u)/P_min)·f₀/fs⌉ with N = 256, because h_max = P_min/N (spec §4.2 step 5).

| System | P(u_def)/P_min | A1 (55 Hz) | A3 (220 Hz) | A5 (880 Hz) | A7 (3520 Hz) | A7 under the LFO: min–max (mean) |
|---|---|---|---|---|---|---|
| Lorenz | 1.73 | 1 | 3 | 9 | 33 | 19–36 (25.6) |
| Rössler | 1.02 | 1 | 2 | 5 | 20 | 19–20 (20.0) |
| Chua | 1.04 | 1 | 2 | 5 | 20 | 19–23 (20.9) |
| Thomas | 1.11 | 1 | 2 | 6 | 21 | 19–23 (21.5) |
| Duffing | 1.00 | 1 | 2 | 5 | 19 | 19 (19.0) |

The cost per second of audio is fs·(n·t_step + t_sample). Above about 200 Hz this is
≈ N·(P/P_min)·f₀·t_step, which no longer depends on fs. Below that, n = 1 and the cost is fs·t_step.
Modulating `param` changes the cost only through P(u), that is, through n. For Lorenz the LFO
makes A7 cheaper (mean 25.6 sub-steps against 33 at the default). For the other systems it changes
nothing measurable.

### 2. Cost of one RK4 step (ns)

| System | numba, engine kernel | numba, scalar locals | JSC A (specialized) | JSC B (port), mono | JSC B (port), mega | JSC A, 2 states interleaved (per state) |
|---|---|---|---|---|---|---|
| Lorenz | 52.7 | 22.0 | 21.8 | 53.5 | 54.7 | 11.2 |
| Rössler | 50.3 | 19.9 | 19.8 | 52.7 | 54.7 | 10.2 |
| Chua | 63.8 | – | 38.9 | 58.1 | 58.9 | 20.0 |
| Thomas | 137 | – | 116 | 131 | 128 | 86 |
| Duffing | 140 | – | 39.4 | 89.4 | 81.3 | 25.6 |

For reference, numba with scalar locals and two Lorenz states interleaved costs 11.3 ns per state.

- **Code structure matters, the language does not.** The array-based structure (scratch arrays
  k1…k4 and tmp, 3-iteration loops) costs about 2.4× the scalar version, in numba and in JS
  alike. The specialized JS matches native code to within 1 ns per step. The dispatch of `rhs` as
  an argument is not the cause: in a side experiment (not in the script), numba with the RHS
  hard-coded but the same arrays took 54 ns.
- **The step is latency-bound.** 22 ns is about 70 cycles at 3.2 GHz.
  - The dependency chain of a Lorenz step is about 70 cycles. Each of the four stages is
    roughly sub → mul → sub, then mul → add for the next stage input. FADD takes about
    3 cycles and FMUL about 4.
  - The ≈ 75 floating-point operations alone would take only ≈ 20 cycles.
  - Two independent states in one loop cost 11 ns each, which confirms the chain is the limit.
  - No language shortens this chain. WebAssembly, like JS, does not fuse multiply-adds, so it
    would execute the same chain.
- **Thomas** has 12 `sin` calls per step, and they sit on the critical path. They account for most
  of its cost.
- **Duffing** is cheap in JS, because its `cos(z)` is off the critical path (z′ = ω does not depend
  on x or y). It is expensive in the numba engine kernel (140 ns).
- **Megamorphic code** (one copy shared by all systems) costs JSC at most about 10 % here.

### 3. Python engine

Real-time factor (RTF: seconds of audio per CPU second) of one box with a static knob:

| System | Measured | A1 | A3 | A5 | A7 |
|---|---|---|---|---|---|
| Lorenz | process(), 512-sample chunks | 163 | 87 | 37 | 11 |
| | process(), 128-sample chunks | 84 | 58 | 31 | 11 |
| | render_tuned alone | 352 | 124 | 43 | 12 |
| Rössler | process(), 512 | 168 | 113 | 62 | 19 |
| | process(), 128 | 85 | 71 | 45 | 17 |
| | render_tuned alone | 381 | 187 | 80 | 20 |
| Chua | process(), 512 | 151 | 101 | 52 | 15 |
| | process(), 128 | 81 | 64 | 40 | 14 |
| | render_tuned alone | 304 | 157 | 65 | 16 |
| Thomas | process(), 512 | 95 | 56 | 22 | 7 |
| | process(), 128 | 58 | 44 | 19 | 7 |
| | render_tuned alone | 149 | 72 | 25 | 7 |
| Duffing | process(), 512 | 94 | 58 | 27 | 7 |
| | process(), 128 | 62 | 38 | 23 | 7 |
| | render_tuned alone | 144 | 73 | 30 | 8 |

- **Each `process` call has a fixed cost of about 22 µs.** The Lorenz A3 fit gives 22.5 µs per call
  plus 0.20 µs per sample. The fixed part is numpy temporaries (`np.full`, three `np.interp`, array
  arithmetic) plus Python call overhead.
- **The kernel is only part of the time at 128-sample chunks** (`breakdown.png`): 36–53 % at A1,
  48–67 % at A3, 65–84 % at A5 and 86–94 % at A7. The rest is the numpy stages.
- **A whole patch** (LFO → Lorenz A3 → Output) renders at RTF 80 with 512-sample blocks and RTF 43
  with 128-sample blocks.
- **The rule of thumb "≈ 10× real time per box" holds only in the top octave** (7–19× at A7). At A3
  a box runs 56–113× real time with 512-sample blocks.
- This only matters for offline render speed: Python is not the real-time engine (ADR 0001).

### 4. JavaScript box per render quantum (JSC)

Microseconds per 128-sample quantum, static / LFO. In brackets: the number of such boxes that fit
in 50 % of one core (1333 µs):

| System | A1 | A3 | A5 | A7 |
|---|---|---|---|---|
| Lorenz | 3.6 / 3.6 (368 / 365) | 8.3 / 6.5 (160 / 204) | 24.6 / 18.9 (54 / 70) | 91.0 / 70.8 (14 / 18) |
| Rössler | 3.3 / 3.5 (404 / 381) | 5.1 / 5.3 (262 / 249) | 12.3 / 13.4 (108 / 99) | 49.7 / 50.3 (26 / 26) |
| Chua | 5.0 / 5.1 (268 / 261) | 10.1 / 10.1 (131 / 132) | 25.1 / 28.7 (53 / 46) | 101 / 104 (13 / 12) |
| Thomas | 15.0 / 15.1 (89 / 88) | 29.9 / 30.3 (44 / 44) | 89.8 / 87.7 (14 / 15) | 315 / 323 (4 / 4) |
| Duffing | 5.9 / 6.7 (227 / 199) | 10.5 / 10.5 (127 / 126) | 25.9 / 26.2 (51 / 50) | 97.9 / 98.0 (13 / 13) |

- **The per-sample bookkeeping is almost free.** Inside the full box, a sample costs n·t_step(A)
  plus 0–7 ns. Examples: Lorenz A7 takes 711 ns/sample = 33 × 21.5 ns, and Thomas A1 takes
  117 ns against a 116 ns step. The bookkeeping (smoothers, binary search in the 129-point u grid,
  three interpolations, normalization, DC blocker, safety check) does not depend on x. The CPU
  therefore runs it in parallel with the RK4 chain.
- **Compared with Python**, the JS box is 1.3–9.5× faster than `process()` at 128-sample chunks.
  The gap is largest at low notes, where Python's per-call overhead dominates. Against numba's
  `render_tuned` alone the JS box is 1.2–3.6× faster, which is the structural factor of §2.

### 5. Many boxes in one engine loop

| Patch (all boxes LFO-modulated, summed into one bus) | µs per quantum | Sum of single-box costs (µs) | % of the 2667 µs budget |
|---|---|---|---|
| 5 boxes: each system at A3 | 67 | 63 | 2.5 |
| 40 boxes: 8 of each system at A3 | 521 | 502 | 20 |
| 20 boxes: every system × {A1, A3, A5, A7} | 982 | 918 | 37 |
| 40 boxes: 2 × every system × {A1, A3, A5, A7} | 1960 | 1836 | 74 |
| 10 boxes: Thomas at A7 | 3115 | 3231 | 117 |

The cost is linear in the number of boxes, within about 7 %. At these sizes there are no cache or
interference effects; each box's state is a few hundred bytes.

### 6. A JIT hazard (qualitative)

In one benchmark sequence, the generated code of the Rössler and Duffing boxes first ran briefly
(38 quanta) with a `Float64Array` control input and then with no input (`null`). Those boxes then
stayed 1.4–2.8× slower for the rest of the run. Rössler A1, for example, took 7.0–7.8 µs per
quantum against 2.7–3.3 µs, over 6000 quanta in each of 5 independent runs.

- A standalone reproduction showed the slowdown twice: 7.7–7.9 µs against 2.8 µs.
- A long warm-up (1500 quanta) did not trigger it.
- The same reproduction placed at the end of the full benchmark did not trigger it either.

The likely cause is a failed type speculation in the JIT, followed by recompiled code that is
less optimized. I could not reproduce it reliably, so treat it as a warning, not a number.

## Conclusion

- **One box is cheap.** In JS at 48 kHz, one box costs 0.2–0.4 % of an M1 Pro core at A3 (Thomas
  1.1 %) and 1.9–3.9 % at A7 (Thomas 12 %).
- **Boxes in real time at ≤ 50 % of one core** (JSC, this machine):

  | Note | Boxes (Lorenz, Rössler, Chua, Duffing) | Boxes (Thomas) |
  |---|---|---|
  | A3 | 125–260 | 44 |
  | A5 | 46–108 | 15 |
  | A7 | 12–26 | 4 |

  Rule: boxes ≈ 0.5/(fs·n·t_step).
  - A patch spread evenly over A1–A7 and all systems averages 46 µs per box per quantum, so about
    29 boxes fit.
  - A v1-sized patch of 4–16 boxes uses a few percent of the core at mid notes. At A7 only 12–26
    boxes (Thomas excluded) fit in the 50 % budget, so 16 boxes all in the top octave would not.
  - The limits are the top octave and Thomas: 10 Thomas boxes at A7 do not run in real time.
- **WebAssembly is not needed for speed.**
  - The specialized JS matches native LLVM code to within 1 ns per step (Lorenz 21.8 against
    22.0 ns), because the step is latency-bound.
  - WebAssembly, which like JS does not fuse multiply-adds, would run the same dependency chain.
  - What matters is code structure: a literal port of the array-based Python kernel is about 2.4×
    slower, in either language.
- **ADR 0002** guesses JS is "1.5–3× slower than native". For this loop that is pessimistic: the
  gap is about 0 when the code is specialized. Its claim of "dozens of boxes" is right for
  ordinary notes, but not for the top octave.

**Uncertainties.**

- **Engine.** I measured JavaScriptCore only, not V8. Both compile monomorphic float64 loops into
  unboxed register code, so I expect V8 within roughly ±30 %. That is an estimate from general JIT
  behavior, not a measurement.
- **Hardware.** This is a fast core. Mid-range laptops or phones may be 2–4× slower per core (also
  an estimate). Divide the box counts accordingly.
- **Not in a real AudioWorklet.** The benchmark excludes the browser's per-quantum overhead (buffer
  copies, the `process()` call), thread scheduling, GC from other code and deadline jitter. The
  50 % margin is meant to cover these.
- **Load.**
  - Repeated measurements spread by about ±5 % for step costs. For example, numba Lorenz gave
    50.7, 56.7 and 52.7 ns in three runs, and JSC Lorenz A gave 21.8–23.1 ns.
  - The spread is up to about 20 % for single-box costs at low notes.
  - The reported numbers are minima over repeats, so if anything they are pessimistic.
- **Sample rate.** Only 48 kHz was measured. At 44.1 kHz the cost of high notes per second of audio
  is the same (the N·f₀ regime), and low notes cost 8 % less.

## Recommendations

1. **Write the TS kernel per system, with scalar locals.** Generate it from the symbolic equation
   source the roadmap already plans. A literal port of `rk4_step(rhs, x, p, k1…k4, tmp)` costs
   2.4× for Lorenz and Rössler and 1.5–2.3× for Chua and Duffing. Keep the persistent state in a
   `Float64Array`: load it into locals at the start of each quantum and store it back at the end.
2. **Keep the hot code monomorphic.**
   - One generated function per system.
   - The same argument types on every call. When no cable is plugged, pass a control
     `Float64Array` filled with the knob value, never `null` (see §6).
   - No allocation in `process()`.
3. **Do not plan WebAssembly for speed in v1.** Revisit it only if profiling on the slowest target
   hardware calls for it. Even then the gains would come from structure, not the language:
   stepping two boxes interleaved in one loop gave a measured ≈ 1.9×.
4. **Give the engine a CPU budget model.** Cost per box ≈ fs·n(u, f₀)·t_step(system), with t_step
   from a per-system table (≈ 20, 20, 40, 115 and 40 ns for Lorenz, Rössler, Chua, Thomas and
   Duffing on this machine). Use it to show a CPU meter and to warn before overload. The top
   octave and Thomas are the expensive cases.
5. **If more headroom is needed, these are the cheapest levers, in order:**
   1. Per-system `steps_per_period = 128` where `resolution.md` finds it sufficient (Lorenz,
      Rössler, Chua, Duffing). This halves the cost of high notes.
   2. Lorenz's h_max is set by P_min = P(u = 1), so at the default it takes 1.73× more steps than
      N = 256 per period. Using h = P(u)/N per sample would make the cost flat in u. This is an
      accuracy decision for you.
   3. A cheaper `sin` for Thomas. This breaks bit-for-bit agreement with the reference.

   If oversampling is adopted for the top octave (`aliasing.md`), the RK4 work there barely
   changes: n is already ≥ 19 and the step is fixed by h_max, so it grows by a few percent at
   most. The added cost is the decimation filter, which this study did not measure.
6. **Design the cross-engine tests for non-bit-exact engines.** JavaScriptCore reproduced numba bit
   for bit for all five systems, including the ones with sin and cos. V8 ships its own sin/cos, so
   for Thomas and Duffing compare short horizons or statistics, not long chaotic trajectories.
7. **Before accepting ADR 0002, run `rk4_bench.html`** in Chrome and on the slowest device you care
   about. It takes about 30 s once `cost.py` has written its config.
8. **Optional, offline Python speed.**
   - Render with large blocks (≥ 512), because each `process` call costs about 22 µs.
   - A scalar, specialized numba kernel would be 2.4× faster at high notes, with bit-identical
     output (verified for Lorenz and Rössler).

## Engine observations (not changed)

- **ADR 0006 overstates how uniform the cost is.** It says the cost per sample is ⌈N·f₀/fs⌉ "whatever
  the system". The spec and the catalog use h_max = P_min/N, so n = ⌈N·(P(u)/P_min)·f₀/fs⌉.
  Lorenz at its default needs 1.73× more: 5 sub-steps instead of 3 at A4, 33 instead of 19 at A7.
  ADR 0002's "about 3 sub-steps per sample at 440 Hz" also understates Lorenz.
- **The numba kernel structure is slow, though not wrong.** `rk4_step` with `rhs(x, p, out)` and
  scratch arrays is 2.4× slower than a scalar-local version that gives bit-identical results:
  52.7 against 22.0 ns per step for Lorenz. Duffing costs 140 ns per step there, against 39 ns in
  specialized JS.
- **`Dynamical.process` has about 22 µs fixed cost per call**, from numpy temporaries and three
  `np.interp` calls (μ and σ are interpolated inside `_audio`). In mono, the DC blocker also runs
  twice on identical data. Both are minor.
